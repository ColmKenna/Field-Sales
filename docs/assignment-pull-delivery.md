# WI-025 — Pull transfers from the receiving rep

A receiving rep's Territory page now offers Add assignment and Take over from another rep beside the summary. Add choices label explicit holders, such as “Rathdrum — Aoife's”. Selecting one opens “Transfer Rathdrum from Aoife to Niamh?” with only that assignment selected. Take over chooses a giving rep and opens their full assignment review with the receiver already set. Both routes use WI-024's transfer preview, confirmation, planner and atomic assignment/history save.

## Implementation and boundaries

Assignment options supply a trusted holder subject, label and assignment ID only for areas the actor can manage. Choice keys bind the target, explicit assignment ID and giving subject; changed choices require a reload instead of silently switching the giving rep. Free areas and areas inherited only from a broader assignment retain ordinary Add behavior. Already-owned explicit choices are disabled and rejected on the server; direct API calls still enforce same-level uniqueness and now guide the user toward a reviewed transfer.

Take over supplies giving reps with existing assignments, excluding the receiver. Current reporting lines scope Sales Managers; Head Office retains existing cross-team authority. Trusted inactive giving reps remain eligible. Add choices retain their active-geography restrictions, while Take over follows the existing transfer rules for archived and empty geography.

The Razor Transfer page validates pull context against its current API review, prefills the receiver, preserves exclusions and shows the ordinary impact preview. Receiver context survives a refreshed proof, cancellation and save. Return destinations use the known Territory route and validated subjects. Push transfers keep the giving-rep return destination. Selecting nothing keeps the selection controls and receiver visible without requesting a new receiver or saving.

No assignment planning or write/history logic changed. There are no migrations, package/runtime changes, visit handover, leaving-rep questions, temporary batches or specialist permissions in this item. The historical specification's superseded duplicate-message quotations are retained; obsolete guidance has been removed from running UI/API.
