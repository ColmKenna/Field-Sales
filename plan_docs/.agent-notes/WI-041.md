## Key facts found while planning

- WI-040 left T-01 showing "Sign in again to send N items" with **Sign in** (calls `TabletApp.SignInAsync()`, the entry screen's
  browser flow). Success runs `TabletDevice.CompleteSignInAsync`, which bumps the session version; `MainLayout` re-keys `<main>`, so
  the Sync page reopens for the signed-in rep with Sync now. `SyncNotices` keeps the page's notice per rep and session.
- `TabletApp.SignInAsync()` returns null on success **and** when the rep closes the browser; it returns
  `SignInNeedsConnection` ("Sign-in needs a connection. Try again when you have signal.") only after a network failure, so without
  signal today the browser opens on an error page.
- `StoredTokenSource` clears tokens on a refused refresh; the local 24-hour window (I3.1) still lets the rep reopen and capture
  offline (`Should_AskForSignIn_When_TheRefreshIsRefused` checks `EnterAsync(false)` → Home).
- Exactly-once is WI-039's: confirmed items move to Sent immediately; each Sync reads the queue fresh; a lost confirmation is re-sent
  and answered `AlreadyReceived`.
- No automatic Sync exists anywhere (T1.3). `Sync.razor` starts a Sync only from the Sync now button.
- `SessionTablet` (fake identity host) and `TestTablet`/`FakeReceiver` (fault controls from WI-040) cover the Core scenarios;
  `TabletAppAdapter` fakes `TabletApp` for screen tests.

## Approved decisions (D1–D7)

| # | Proposal |
|---|---|
| D1 | The interrupted Sync is identified by a **one-shot resume request** made only when the rep taps Sign in on T-01 (after a Sync stopped for sign-in). It names the rep and the session it was made in, lives in `TabletApp` memory (next to `SyncNotices`), and is honoured once by the first Sync screen of a **new session for the same rep**. |
| D2 | The request is dropped when the sign-in fails or is cancelled (the session didn't change), when another rep signs in, or when the session ends (sign-out, 24-hour lock). It is never made by signal returning or by the app resuming (T1.3), and an app restart forgets it. |
| D3 | The resumed Sync is an ordinary Sync of whatever is waiting **now** (the queue is read fresh): items captured after the failed Sync go too, confirmed items are never re-sent, and a lost confirmation is re-sent and confirmed as already received. The rep sees "Sending 1 of N…", then the usual outcome (Home if everything went). |
| D4 | T-01 adds I-03's line under Sign in: "After sign-in, this Sync resumes automatically." (I-03 is a layout proposal, MI-08.) |
| D5 | US-004 S3: tapping Sign in without signal does not open the browser; it says "Sign-in needs a connection. Try again when you have signal." (existing text) and leaves everything as it was. A cancelled browser stays silent, as today. |
| D6 | US-004 S4 needs no new behaviour: within the local 24-hour window an expired online sign-in still allows capture; it is characterised by a test. |
| D7 | No server, API, identity-host or contract change. MI-62 untouched. |
