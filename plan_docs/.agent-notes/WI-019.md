## Findings and accepted decisions

At the pre-implementation baseline, Location stored optional Eircode text but no
coordinates or precision. Town has
only identity/name/parent/archive/version fields. Existing geography CSV is
exactly Region,County,Town, with no coordinate columns. No lookup adapter or
provider configuration exists. The prior decision to accept Head Office CSV or
manual geography entry is preserved; coordinate ingestion needs extending here.

The user first answered: “recommend one, eircode is just the fallback so
can be removed or left optional”. After the recommendation and two remaining
policy questions, the user answered: “use Town coordinates first and leave
Eircode lookup / yes both”. This accepts the following rules:

1. Town coordinates are the first default. Keep Eircode text and optional
   server-side lookup, disabled initially. No purchased lookup service is
   required to deliver this item. This supersedes the source's Eircode-first S1.
2. If neither source supplies coordinates, save the Location with a clear
   Position needed flag. No fabricated pin or precision. This explicitly
   amends the source assumption that every new Location receives a position.
3. Head Office supplies Town coordinates through CSV or manual entry.
4. Changed Eircode/Town recalculates unconfirmed positions and retains history.
   A Confirmed on site position is always preserved by automatic defaulting.
5. Lookup requests and credentials remain on the server.

There are no unanswered business-rule questions. The full plan and enumerated
test scenarios below are approved.

Provider recommendation: Postcoder by Allies Computing, if the optional
fallback is enabled later. It appears in Eircode's approved provider list, has
a direct position endpoint for Irish Eircodes and offers one-off credit packs.
Autoaddress was also reviewed; its API provides coordinates plus accuracy, but
its published entry plan is a recurring subscription. The recommendation is an
engineering judgment for occasional optional lookups, not proof of purchased
coverage or rights for this application. Do not purchase/contact either provider.
Before live enablement, check the actual account's Eircode feature, storage use,
coverage and credentials. No mandatory licence purchase blocks the proposed
Town-first implementation under the user's override.

Sources checked 2026-10-02:
- https://postcoder.com/docs/address-lookup/position (direct Irish endpoint,
  4.5 credits per request; Eircode must be enabled on the account).
- https://postcoder.com/pricing (one-off credit packs, 12-month validity).
- https://postcoder.com/terms and the Eircode licence linked from its portal
  (not an executed application-specific contract).
- https://autoaddress.com/pricing/ and https://autoaddress.com/geocode/
  (recurring entry plan and returned coordinate accuracy).

Accepted priority: preserve an existing Confirmed on site
position; otherwise use the Town pin as the initial default; if the Town lacks
coordinates, use an optional enabled Eircode lookup; if neither supplies a pin,
save with Position needed. When a Town pin exists, no external lookup runs.
The original Eircode-first S1 must be explicitly reported as superseded by the
user's fallback instruction.

Other defaults (inferred during planning, now accepted by plan approval): optional lookup
unavailable, not found or returning invalid coordinates leaves Position needed
when the Town has no pin. No background retry service is included in this slice.
No lookup on unrelated/no-op edits. Changing
or clearing an Eircode and changing Town must not leave an unconfirmed pin
mislabelled as belonging to an old input. Town coordinate edits do not silently
bulk-move existing shop pins; they apply on the next explicit recalculation.
Preserve confirmed positions and history when changing unrelated details.

Read-only source verification on 2026-10-02: official Eircode documentation
states ECAD includes geo-coordinates and lists approved providers. This is not
a selected provider, a purchased licence or verified application coverage.
Sources: https://www.eircode.ie/business/products-and-services and
https://www.eircode.ie/business/feature . No provider was contacted or purchased.

## Approved Scenario Review matrix

1. Should_SaveTownDefaultOrOptionalEircodeFallback_When_FirstLocationIsCreated
   → Hickey's Customer and first Location save together using Town precision;
   when Town lacks a pin and optional lookup is enabled, successful lookup uses
   Eircode precision. Disabled lookup never prevents ordinary Town defaulting.
2. Should_SaveTownPrecision_When_LocationHasNoEircode
   → A Location in Laragh uses its stored Town coordinates with Town precision.
3. Should_SavePositionNeeded_When_OptionalLookupIsUnavailableAndTownHasNoPin
   → Timeout/service failure permits saving with Position needed; never present
   a successful Eircode lookup or a fabricated Town pin.
4. Should_SavePositionNeeded_When_OptionalEircodeCannotBeResolved
   → With no Town pin, not found or invalid provider output saves the missing
   position state without inventing coordinates or saving a partial Customer.
5. Should_SavePositionNeeded_When_TownAndLookupHaveNoCoordinates
   → Save with null coordinates and null precision; show Position needed.
   Disabled lookup and missing/cleared Eircode must also allow saving.
6. Should_RecalculateUnconfirmedPositionAndRecordHistory_When_AddressInputsChange
   → Additional Location creation, changed/cleared Eircode and changed Town use
   the agreed resolver, history and precision; old pins never acquire a false
   new-source label. Preserve the previous position in history when it changes.
7. Should_PreserveConfirmedPosition_When_AddressInputsChange
   → Confirmed on site data remains intact and no automatic lookup replaces it.
   Tablet GPS capture itself remains WI-143.
8. Should_AvoidLookupAndHistoryNoise_When_UnrelatedOrNoOpEditIsSaved
   → Name/Type-only or unchanged edits preserve position/history and still honor
   existing rowversion and archived-reference rules.
9. Should_SaveValidTownCoordinatesAtomically_When_HeadOfficeUsesManualEntryOrCsv
   → Latitude/longitude must be paired and within range; unchanged names/IDs and
   repeated imports remain safe; old three-column CSV stays supported. Reject
   invalid files without partial updates and retain invalid manual input.
10. Should_RejectStalePositionChanges_When_LocationOrTownChangesDuringLookup
    → Lookup returning after another user's edit cannot replace newer input,
    Main selection or a confirmed pin; valid changes/history stay atomic.
11. Should_PreserveDirectoryData_When_CoordinateSchemaIsAddedOrAppRestarts
    → Upgrade WI-018 data without fabricating missing positions; retain IDs,
    Contact links/Main, Town/Types, coordinates/precision/history on restart.
12. Should_ProtectCoordinateChanges_When_RoleScopeOrAntiforgeryIsMissing
    → Head Office/current access, server-held credentials, invalid input and
    browser antiforgery protect the new routes; no browser/tablet geocoding.

Source S1's No Visit Schedule and Unassigned lists belong to other items and are
not part of these two coordinate acceptance criteria. Existing test assertions

conditions, existing Towns lacking positions, stale lookup results overwriting
newer edits, and external latency inside database transactions. Review the
actual provider documentation and policies before wiring requests.

No Visit Schedule/Unassigned lists and coverage assignment, Main retirement
(WI-020), bulk coordinate changes to existing shops, buying a licence or
contacting providers, main integration and alternative front ends.
