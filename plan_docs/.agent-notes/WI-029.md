## Repository findings

- Restriction Groups live in **CatalogueDb** (`RestrictionGroup : NamedReferenceItem`,
  `Products.RestrictionGroupId` FK restrict). `RestrictionGroupListStore` already defines the
  archive/un-archive notes keyed by `PermissionSource = "restriction-permissions"`; required sources
  are `["products"]` only, so production shows no permission count yet.
- `IReferenceUsageSource` doc: "Retirement reads must share the delete transaction."
  `ReferenceListStore.RetireAsync` reads usage inside a serializable CatalogueDb transaction.
  WI-009's approved checkpoint (`docs/catalogue-brand-reference-checkpoint.md`): a reference stored
  elsewhere must "join the coordinated transaction or maintain durable local reference protection"
  before retirement may ignore it. WI-011 repeats this for WI-029.
- `RestrictedProductVisibility.VisibleToRep(products, groups, permittedGroupIds)` is the single
  visibility rule; WI-043 must feed it WI-029's current permissions.
- Reporting lines (`RepReportingLine`, one manager per rep), territory assignments and append-only
  `AssignmentHistory` (INSTEAD OF UPDATE, DELETE trigger; captured labels; UTC; formatter
  "dd MMM yyyy HH:mm UTC") live in **DirectoryDb**. `CoverageReadStore.RequireRepAccessAsync`
  denies foreign reps to managers for coverage reads, so S4's "view" needs a different read rule.
- Trusted identity: `CoverageStaffProvider` (lookups must happen before any DirectoryDb
  transaction; fails closed with 503). Current roles are refreshed per request in the API.
- API: `/coverage` group requires `ManageCoverage` (Sales Manager or Head Office User + scope).
  `GuardAsync` maps forbidden/validation/conflict/identity/SQL 547/1205/2601/2627.
- Web: `/Coverage` folder requires `ManageCoverage`; `CoverageApiClient` holds server-side tokens;
  `Territory.cshtml` is the manager-page pattern (T-3.1.3). No M-14 frame exists, only decisions.
- Tests on main: real API + SQL Server (Testcontainers) + fake staff directory in
  `tests/Integration/FieldSales.Web` (`CoverageReadApplication`, `ProductApplication`,
  `StaffWebsiteFactory`); SQL-level tests in `tests/Integration/FieldSales.Api`.
  `ReferenceListIntegrationTests` (WI-011 tests 9–11) inject a fake `PermissionUsageSource` with
  `AddSingleton<IReferenceUsageSource>`; a real registration would duplicate the key.

| D2 | Self-change | Nobody changes their own permissions, Head Office included; their own page is view-only. |

| D4 | Archived groups (card DP3, MI-45) | No new grant on an archived group. Removal stays allowed and is recorded normally, because un-archiving restores held permissions. The per-rep view lists active groups plus archived groups the rep holds, marked "Archived — no effect while archived", with Remove only. |
| D5 | Storage | CatalogueDb, code under `FieldSales.Api/Coverage`: append-only `RestrictionPermissionChanges` (captured rep/actor/group names, no FK) plus current-state `RestrictionPermissions` (PK rep+group, FK restrict to `RestrictionGroups`), written in one serializable catalogue transaction. Joins the retirement transaction as WI-009/WI-011 require. The reporting line is read in a serializable DirectoryDb transaction held open until the catalogue write commits, so a concurrent reporting-line change waits. Rejected: DirectoryDb storage (remote, non-atomic count and delete protection). |
| D6 | Repeated or stale changes | Each change carries the last change id the page showed. If the state moved on (other manager, double submit, already granted), refuse with "This permission changed. Reload before saving." and record nothing. |
| D7 | Deleting a group whose permissions were all removed | Allowed when no product uses it (usage counts current grants only); history keeps the captured group name. A group with a current grant offers Archive only. |
| D8 | Eligibility | Grant requires an active Field Salesperson in the trusted staff directory. Removal also works for a rep who has since become inactive. Identity lookup failure fails closed (503), nothing recorded. |
| D9 | Interfaces for later items | Register the real `restriction-permissions` usage source (current grants) and add it to the list's required sources. Expose in-process `RestrictionPermissionReader.CurrentGroupIdsAsync(repSubject)` for WI-043 to pass to `VisibleToRep`. No new tablet endpoint. |
