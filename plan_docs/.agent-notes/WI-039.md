## Approved decisions (D1–D11)

| # | Decision |
|---|---|
| D1 | Identity is the **tablet GUID alone**. The server stores a SHA-256 of the body, not part of identity. Same id + different body: keep the first version, record the re-send with changes on the ledger row, still confirm. Today the tablet can't change an item after Ready to Send; WI-046 and Call corrections inherit the question. |
| D2 | One `PUT` per item. 201 `Received` first time, 200 `AlreadyReceived` after; the tablet marks Sent on either, locally and immediately after each confirmation, before the next item. Lost confirmation or a kill between server commit and local mark → next Sync re-sends → `AlreadyReceived`. No batches, no two-phase. |
| D3 | Calls first, then Orders, oldest saved first in each group. No server-side dependency; an order's `callId` matches whenever both arrived. |
| D4 | **MI-52 answer — technical faults:** (1) corrupt/unreadable body, (2) unknown schema or version, (3) incomplete structure (order: id equals path id, state ReadyToSend, location, orderedBy, capturing rep, takenOn, snapshot ref, ≥1 line each with id, product, quantity > 0, unit, price ≥ 0, snapshot ref), (4) capturing rep ≠ token subject, (5) id already used by another rep (409), (6) too large (413). Fault → item stays unsent, Sync continues with the next item. **No business-rule or catalogue/directory lookup on receive** (BR-NEW-006). A duplicate is not a fault (D2). |
| D5 | Tablet Unsent DB v1 → v2 adds a `sent` table; marking Sent moves the row from `work` to `sent` in one transaction. Readers of `work` (count, sign-out warning, shop retention, fingerprint, OrderStore) exclude Sent with no other change. `OrderStore.AddLine` refuses an id present in `sent`. Sent items are kept (no purge here). |
| D6 | New SQL Server **`OrderingDb`** (AppHost resource, EF Core, migrations, DatabaseStartup, test reset list). `ReceivedWork` ledger: Id PK (tablet GUID), Kind, RepSubject, ReceivedUtc, ContentSha256, Body verbatim, resend-with-changes count/last time. `Orders`: Id PK/FK to ledger, Status **Pending**, LocationId, OrderedById, CapturingRep, TakenOn, CallId, snapshot version/built, ReceivedUtc. One transaction; concurrent duplicate PK → re-read → `AlreadyReceived`. Lines stay in the body (WI-067 decides line tables). Calls live in the ledger only. |
| D7 | Call body **not defined here** (WI-047 owns contents, structural checks and the snapshot reference). Server checks a Call only as a JSON object within the size limit (and `id`, if present, equal to the path id) and stores it verbatim. |
| D8 | Sync sequence: token → uploads → space check → download. Download runs whatever the upload outcome. Not enough space stops only the download. 401/403 stop everything. Network drop or 5xx stops remaining uploads but the download is still attempted. |
| D9 | "Sending 2 of 3…" in the progress region, then "Downloading your day…". All sent → Home (as now). Some not sent → stay on Sync with "N items not sent. They'll send next Sync." Causes are WI-040. |
| D10 | Pending only; no head-office screen. |
| D11 | Upload contract in `FieldSales.Snapshot.Contracts` as `TabletUploadContract` (paths, receipt, size limit). Snapshot document unchanged, no version bump; developer reviews as contract owner. Paths planned: `PUT /tablet/uploads/orders/{id}`, `PUT /tablet/uploads/calls/{id}` (test prefix `FakeSnapshotServer.UploadPathPrefix`). |
