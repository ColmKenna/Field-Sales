## Findings

- Customers and Locations live in the Directory database (`DirectoryDbContext`); tiers in the Catalogue database
  (`CatalogueDbContext`); orders in the Ordering database. The API process has all three contexts.
- Accepted orders keep their lines in the received body (`ReceivedWork.Body`, `TabletOrder` JSON); the snapshot builder reads them
  that way (`TabletSnapshotBuilder.ReadRecentOrdersAsync`).
- The customer record (`/HeadOffice/Customers/{id}`) has one section (Locations) and reads `CustomerDetails` from the Directory API.
- The engine resolves a product for the tiers a customer holds (`PriceResolver.Resolve(product, tiers, quantity, date)`), and
  `PriceTier.ToEngine()` / `Product.ToPricedProduct()` map stored records into it.

## Decisions (assumed, developer pre-approved)

- **D1 Link storage:** a table `CustomerPriceTiers` (CustomerId, PriceTierId) in the catalogue database beside the tiers, keyed by
  both, with a foreign key to the tier. The customer is in another database, so it is checked against the Directory on save rather
  than by a foreign key (inferred).
- **D2 Editing (H21.1):** a "Pricing" section on the customer record: "Tiers: Tier B, Suncare Deal 2027" (or "Tiers: none —
  Base Price plus any break"), a checkbox per tier with its terms, "Update sample" (recalculates with the ticked tiers without
  saving) and "Save tiers". The set replaces the customer's tiers (`PUT /pricing/customers/{id}/tiers`); the same tier sent twice
  is held once (inferred).
- **D3 Sample (H21.2):** rows "Product · Base · This customer · From", priced by the engine for today at the product's smallest
  orderable quantity, with the ticked tiers. The products are the 5 on the most of the customer's last 20 accepted orders (ties by
  name) (inferred), plus a search ("Check another product", first 5 matches). With no accepted orders it says so and offers the
  search. `GET /pricing/customers/{id}/sample?tierId=…&find=…`.
- **D4 Locations price against their customer's tiers:** one service (`CustomerTierPricing`) finds a location's customer, its tiers
  and the engine inputs; the sample uses it, and WI-064's snapshot will.
- **D5 Removing a tier** changes prices from then on only; captured orders keep their captured line prices (the server never
  re-prices, WI-059). Tablets see it once tiers reach the snapshot (WI-064).
- **D6 Access:** the `HeadOfficePricing` API policy; the customer record is under `/HeadOffice` (Head Office User).
- **D7 Out of scope:** tiers on the tablet (T-6.4.2, WI-064), promotions by tier (E18), drift (E19), "Held by N customers" on the
  tier list (H20.3).
- **D8 Finish:** push, PR, merge after CI (merge commit, branch kept), update local main (pre-approved).
