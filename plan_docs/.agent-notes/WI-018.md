## Clarification and proposed defaults

The user clarified: “a user can be main for two different shops, a shop can
only have one main”. In this context that means the same Contact can be Main
at multiple Locations, while each Location has one Main. Contacts are people,
not staff login accounts, and do not belong exclusively to one Customer.

The source explicitly makes the first linked Contact Main, but its Mary example
also leaves Wicklow without a Main after Mary is linked there. Proposed
reconciliation (initially inferred, now accepted with plan approval): retain automatic first Active
Contact designation; demonstrate that Main choices are independent by starting
Wicklow with another Main, then linking Mary there without replacing that Main.
Locations with no Contacts can remain empty. Do not change card/spec content.

A second optional clarification was presented: when only Inactive Contacts
exist, automatically make the first newly linked Active Contact Main; retain
the Inactive links behind Show inactive and reject Inactive Contacts as new
links/Main choices. This is the proposed default for approval unless corrected.
Initial Approved accepted that default. It does not implement WI-020's
departing-Main/gap workflow.

Other approved defaults (initially inferred):

- Required trimmed name, max 200 characters; names are not unique. A required
  active Contact Type at creation/new assignment; retain unchanged archived
  Types on edits, with the existing `(archived)` label.
- Phone/email optional, trimmed, bounded (phone 50/email 254), blank becomes
  null; format checks only, no verification or external lookup.
- Create a Contact as Active with at least one initial Location, atomically;
  allow additional links across Locations/Customers using the same Contact ID.
- Active/Inactive state belongs to the Contact globally. Inactivating a
  non-Main Contact is allowed; if Main anywhere, reject the status change with
  an explanation until WI-020's replacement/retirement flow exists. No delete.
- Relinking the same Contact to the same Location makes no duplicate and does
  not alter the current Main. Display an already-linked message.
- Set Main requires an Active linked Contact. Replacing an existing different
  Main shows the named confirmation; Cancel changes nothing, and confirmation
  must check the same outgoing Main/version again. A stale confirmation requires
  reload, never silently replaces a newer choice.

## Approved Scenario Review matrix

These names/intent were offered before test code, and initial approval now
covers them plus the inferred defaults above. They derive from S1–S5, the
source's six criteria, its requested edges and predecessor integration rules.

1. `Should_ShowSameContactAtAllLocations_When_ContactIsLinkedToSeveralShops`
   → Create Mary Walsh/Pharmacist with details; link Rathdrum, Arklow and
   Wicklow Town, including different Customers; reopen all shops and the
   Contact to prove one stable person and all links.
2. `Should_SetMainIndependentlyAtEachShop_When_SameContactIsMainAtTwoLocations`
   → Mary is Main at Rathdrum and Arklow; Wicklow's existing different Main
   remains unchanged. Show the exact Main contact label at each shop.
3. `Should_SetMainAndExplainIt_When_FirstActiveContactIsLinked`
   → The first Active Contact becomes Main automatically, with a note; an
   empty Location remains valid before its first Contact arrives.
4. `Should_KeepOutgoingContactLinked_When_MainReplacementIsConfirmed`
   → Show “Replace Mary Walsh as main contact?”, make no change on Cancel,
   then confirm Sean; Mary remains linked and other shops retain their Main.
5. `Should_HideInactiveContactsAndShowCount_When_LocationListIsOpened`
   → With three Inactive Contacts, show Active ones and “Show inactive (3)”;
   toggling reveals all three without deleting/changing IDs or Main selection.
6. `Should_AvoidDuplicateLinks_When_SameContactIsLinkedAgain`
   → Repeated and concurrent links produce one relationship, a useful message
   and no unintended Main replacement.
7. `Should_FillMainVacancy_When_FirstActiveContactJoinsInactiveOnlyLocation`
   → Inactive-only legacy data stays visible through Show inactive; the newly
   linked Active person becomes Main and no Inactive person can be chosen.
   Proposed default from the optional clarification, for approval.
8. `Should_RejectRetirementAndUnlinkOfMain_When_ReplacementFlowIsUnavailable`
   → Attempts from either shop or Contact routes cannot clear Main, retire a
   person Main elsewhere or delete a Contact. A non-Main status edit preserves
   every link and updates all affected inactive counts.
9. `Should_SaveNothingAndKeepInput_When_ContactDetailsOrLinksAreInvalid`
   → Name/format/length limits, required initial shop/Type, unknown IDs,
   invalid state and invalid multi-shop creation are rejected atomically.
   Nonunique names remain allowed; reject new archived Type assignments and
   preserve unchanged archived Types through unrelated Contact edits.
10. `Should_RejectStaleReplacement_When_MainChangesAfterConfirmation`
    → An old confirmation, absent/malformed version, stale/no-op Contact edit,
    missing/unlinked/Inactive candidate or forged outgoing Main cannot overwrite
    current data; only fresh explicit confirmation replaces it.
11. `Should_PreserveOneMain_When_LinkingAndMainChangesRace`
    → Concurrent first links, two users setting/replacing Main and state changes
    cannot create two Mains, lose required Main or leave partial links; direct
    SQL constraints reject duplicate links/Main violations. Version conflicts
    return useful reload feedback.
12. `Should_CountRealContactsAndKeepLabels_When_ContactTypeIsArchived`
    → Buyer used by 14 real SQL Contacts (including Inactive ones, with multiple
    links) reports 14 Contacts, offers Archive only and keeps their labelled
    Type links. Empty/delete behavior, invalid usage and assignment/retirement
    races remain safe. Replace WI-017's fixture evidence with real records/pages.
13. `Should_ProtectContactChanges_When_AccessOrConfirmationIsInvalid`
    → Head Office role/scope, unauthenticated callers, immediate role removal,
    forged/omitted confirmation and missing antiforgery protect reads/writes.
14. `Should_PreserveDirectoryData_When_ContactSchemaIsAddedOrAppRestarts`
    → Upgrade WI-017's schema with existing Customer/Location/geography/Types;
    preserve them and optional references, restart and read all Contact details,
    links, status and Main choices. Run all prior suites unchanged.
