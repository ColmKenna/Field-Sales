### Needs a decision — previous snapshot generations

Code evidence: `SnapshotStore` retains two completed generations (`RetainedGenerations`); activation
retires only older generations, and background cleanup removes retired rows. Active readers always join
the `active` pointer. Thus after a successful removal Sync, T1 proves no current UI/read exposure, but
the previous authorized generation can still contain the product in local storage. The completed
download file is deleted by TabletSync; captured order lines are separately retained intentionally.

Choose the intended policy before matrix approval:

- **A — active catalogue and new downloads:** preserve the existing two-generation recovery policy.
  T1 checks current reads; no assertion that older recovery copies are erased. This matches the
  implementation plan as approved but needs explicit acceptance against the phrase absent entirely.
- **B — remove older catalogue copies on access reduction:** add a retention/purge scope amendment
  and a test that old generations stop retaining newly denied product facts after successful Sync,
  while captured work survives. This concerns logical stored records, not a promise of forensic
  erasure of SQLite pages/WAL. Preserve failed-Sync atomic recovery in T2.

Do not infer either policy from plan approval. If B is selected, first agree its activation/recovery
boundary and expected test before changing SnapshotStore's existing retention design.
