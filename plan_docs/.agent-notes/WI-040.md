## Key facts found while planning

- `TabletSync.SyncAsync`: token → uploads → space → download (WI-039 D8). Token null → `SignInRequired`, `UploadSummary.None`
  (queue never read). 401/403 during upload stop everything. Network failure **or** 5xx/unexpected answer/bad receipt →
  `UploadStop.Unavailable`, remaining uploads stop, download still tried.
- `SyncMessages` today: `SignInRequired = "Sign in again to sync."`, `NoConnection = "No connection — your work is saved on this tablet"`,
  `NotSent(n)` = "N items not sent. They'll send next Sync." (WI-039). `Failed`, `Cancelled`, `InsufficientSpace` all claim saved
  work is unchanged — untrue since WI-039 when items were sent before the download failed.
- `Sync.razor`: greys Sync now and shows `NoConnection` when `Tablet.Connected` is false; after a Sync shows `notSent` line and
  `outcome.Message`; goes Home only when completed with nothing left unsent. No Sign in action exists on T-01.
- `TabletApp.SignInAsync()` (system browser) is used by `Entry.razor`; after success `CompleteSignInAsync` bumps the session
  version and `MainLayout` re-keys `<main>`, so the Sync page reloads for the signed-in rep.
- `StoredTokenSource` clears tokens on a refused refresh (400/401), so later Syncs ask for sign-in at once; the 24-hour local window
  still allows offline capture. Access tokens last 3600 s; refresh-token absolute lifetime 24 h.
- Harness already present: `FakeSnapshotServer` (`Respond`, `RespondToUpload`), `FakeReceiver.Interfere` (in `TabletUploadTests.cs`),
  `FailingContent`, `TestTokens`, and `SessionTablet` with a fake identity (`Identity.Override` → `invalid_grant`).
- Components tests compile `Sync.razor` against `TabletAppAdapter` (needs a sign-in member for the new action).

## Approved decisions (D1–D8)

| # | Proposal |
|---|---|
| D1 | Causes: **sign-in expired** (no token, refused refresh, or 401) → nothing more uploads, no download; **no connection** = nothing in the Sync got an answer (no item confirmed and the day didn't download because the server couldn't be reached); **poor connection** = the connection failed during uploads but something got through (an item confirmed, or the day downloaded afterwards); **server error** = 5xx/unexpected status/receipt not naming the item → uploads stop, download still tried; refused items (400/409/413) keep WI-039's wording until WI-042. |
| D2 | S2 verbatim: "2 items not sent — poor connection. They'll send next Sync."; one item: "1 item not sent — poor connection. It'll send next Sync." The T-01 wireframe's "Try again when you have signal." loses to the story AC. |
| D3 | S3: "Sign in again to send 3 items" with a **Sign in** button replacing Sync now. Count = finished work still waiting (saved Calls + Ready to Send Orders); "1 item"; nothing waiting → "Sign in again to sync." Sign in runs the entry screen's connected sign-in; afterwards the rep is back on Sync and taps Sync now. Auto-resume, "After sign-in, this Sync resumes automatically." and no-signal handling of Sign in are WI-041. |
| D4 | Server error (not in spec, recommended): "2 items not sent — Field Sales didn't respond. They'll send next Sync." Alternatives: reuse poor connection, or WI-039's cause-less sentence. |
| D5 | Download after a failed upload is still tried in the same Sync (WI-039 D8), never automatically later (T1.3). Visible through "Last synced" (moves only if the day downloaded). One connection sentence only: when the work line says no/poor connection, the day's "No connection" isn't repeated. |
| D6 | Upload worked, download didn't (not in spec, recommended): "3 items sent." / "1 item sent." then the day line: no connection "Your day didn't download — no connection."; failure "Your day didn't download. Sync again to try."; space "There isn't enough free space on this tablet to download your day."; cancelled "Sync was cancelled before your day downloaded." When nothing was sent in that Sync, today's messages stay. |
| D7 | Progress "Sending 2 of 3…" already delivered (WI-039 + device fix); add only a test that progress stops at the item going when the connection drops. |
| D8 | Tablet only: no API, server or snapshot-contract change. Confirmed items move to Sent at once and each Sync reads the queue fresh, so a repeated or resumed Sync never re-sends a confirmed item (answers the card's resume-point question for WI-041). |
