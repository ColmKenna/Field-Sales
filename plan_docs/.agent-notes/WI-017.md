## Scope and proposed defaults

- Two DirectoryDb reference tables, Location Types and Contact Types, with
  name, description, archive state, stable ID and rowversion. An optional
  restrictive LocationTypeId belongs on Location. Existing Locations migrate
  without a Type; no automatic seed Types or guessed classifications.
- Add/edit names and descriptions, Archive used items, Delete unused items
  with plain confirmation, Show archived, and Un-archive. Reuse the existing
  reference-list interfaces/contracts and shared list/retirement/confirmation
  controls. Preserve existing catalogue list behaviour.
- Names required, trimmed, up to 200 characters, case-insensitively unique
  within each list including archived names, as in the predecessor pattern.
  Description optional, trimmed, up to 2,000 characters (inferred defaults
  proposed for approval); blank becomes null. Display descriptions on list
  records. Descriptions are explanatory text, with no operational side effects:
  “Head office — no stock held” does not itself implement stock policy.
- Type is optional on Customer-first-Location, additional-Location and edit
  forms. Only active Types can be newly assigned. A stored unchanged archived
  Type survives unrelated edits, labelled `(archived)`. Clearing is permitted.
  Display the Type on Location records and the Customer Locations table.
- Check Type assignments, actual distinct Location usage and retirement in
  the same serializable DirectoryDb transaction. Existing IDs and relationships
  remain intact. Stale edits/retirement and invalid/missing Types save nothing.
- Both lists join the existing H-17 switcher alongside its five catalogue
  lists. Keep Directory stores and usage sources scoped separately from
  CatalogueDb. Extend shared read metadata compatibly for descriptions/versions.

## Proposed scenario matrix (approval covers these intents)

1. `Should_OfferAndPersistType_When_HeadOfficeTypeIsAdded` — save Location Type
   “Head office — no stock held” with description through H-17; select it on
   first/additional/edit Location forms; reopen records and see the Type column.
2. `Should_PreserveOptionalType_When_TypeIsBlankOrCleared` — untyped creation
   remains valid; existing Locations migrate untyped; clearing a selection saves
   while retaining Customer/Town and the required-first-Location invariant.
3. `Should_PersistNamesAndDescriptions_When_TypesAreCreatedOrEdited` — exercise
   both lists, trim/blank descriptions, valid bounds, restart persistence and
   retained inputs; reject invalid names/overlong descriptions and duplicates
   (including archived names); allow identical names across different lists.
4. `Should_KeepFourteenContactReferences_When_BuyerIsArchived` — fixture-backed
   Buyer shows exact `Used by 14 contacts`, Archive only, cancellation changes
   nothing, confirmed archive retains all 14 links/IDs and archived labels.
5. `Should_DeleteOnlyUnusedTypes_When_DeletionIsConfirmed` — both unused Type
   lists offer plain Delete confirmation; Cancel retains them; Confirm removes;
   direct deletion of a used Type is rejected.
6. `Should_KeepExistingTypeAndRejectNewAssignments_When_TypeIsArchived` — count
   real SQL Location references; active selections exclude archived Types;
   existing forms/records retain labelled links; clearing and unrelated edits
   work; archive after form load prevents new assignment; Un-archive restores.
7. `Should_ShowAllSevenLists_When_H17SwitcherIsOpened` — both Types and the five
   existing catalogue lists are reachable; Show archived, descriptions and
   selected-list form values work without cross-database usage resolution.
8. `Should_SaveNothing_When_TypeOrVersionIsInvalidOrStale` — unknown/missing
   Type, absent record, stale edits/retirement, changed usage after confirmation,
   and missing/duplicate/malformed/unavailable sources fail without mutations.
9. `Should_PreserveReferences_When_AssignmentRacesRetirement` — Type assignment
   versus Archive/Delete and stale Type updates preserve FK integrity and archive
   rules; rejected first-Location Type selection saves neither record.
10. `Should_ProtectFormsAndPreserveData_When_AccessOrSchemaChanges` — Head Office
    role/staff scope, immediate role removal and antiforgery protect reads/writes;
    predecessor migration and restart preserve Customer/Location/geography data;
    complete existing catalogue/customer/geography/staff suites remain green.
