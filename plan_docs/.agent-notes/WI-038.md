## Approved decisions (D1–D9)

| # | Decision |
|---|---|
| D1 | Same product added twice: **one line, quantities summed**, revalidated by `QuantityRules`. |
| D2 | Captured price: winner, source and a `candidates` list. Only the base price exists now (one candidate), so E6 adds candidates without changing the stored shape. |
| D3 | Each line stores `productCode` and `productName` at capture. |
| D4 | Snapshot reference is contract version plus manifest `BuiltUtc`, on the order at start **and** on each line (a line added after a later Sync follows the newer snapshot). |
| D5 | Server model: new `FieldSales.Ordering.Contracts` project (records plus source-generated JSON context) shared by tablet and API. No endpoint, persistence or validation (WI-039 / T-4.1.2). No snapshot version bump. Add it to `FieldSales.slnx` and `FieldSales.Tablet.slnx`. |
| D6 | A product with no base price in effect cannot be added; search shows "No price yet". |
| D7 | "Today" is the tablet's local date via the injected `TimeProvider`. Price is the newest `EffectiveFrom` on or before today. |
| D8 | Unsent count: core `UnsentSummary` (In Progress, Ready to Send, total) plus one status line on the Sync screen. Home is WI-048; the list is WI-042. |
| D9 | Nothing is stored until the first line is added. Each add saves immediately as In Progress. "New Order" always starts a new order. A mistaken line or a left-behind In Progress order cannot be removed or reopened until WI-046. The screen has Save and close, which returns to the shop. |

Implementation points that refine the decisions (all within D1–D9):

- A merged line keeps the price, snapshot and unit it captured first; only its quantity changes.
- A new line must meet the product's minimum and step. Adding to an existing line needs only a positive whole number of steps, and the **new total**
  must meet the rules (so 0.5 kg may be added to 1.5 kg of a 1.0 kg-minimum, 0.5 kg-step product).
- Every add requires the shop to be assigned on the current snapshot, including adds to an existing In Progress order. The order never moves shop.
- The order id is chosen by the screen when it opens, so a repeated add or Save with the same id cannot create a second order.
- Quantity text accepts digits and a decimal point only, so "1,5" is refused rather than read as 15. Text that isn't a number is treated as no quantity, so the
  product's own rule message tells the rep what to enter.
- Error texts are constants on `OrderStore` (`NotAssigned`, `NotDownloaded`, `NoPrice`, `NotChangeable`, `AlreadyReady`).

Other approved points: the footer shows line count and running value (T-07); quantity field opens empty, never prefilled (T7.7);
button wording is "Mark Ready to Send" (T7.4); state lives in the JSON body, not a new column, so `UnsentStore` schema v1 stays
(inferred); EUR only, no currency field (inferred). The developer's approval also covers pushing the finished branch.
