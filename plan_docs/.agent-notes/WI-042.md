## Mapping checkpoint (proposed; waiting for review)

| Server fault | Sentence | Rep's action |
|---|---|---|
| `incomplete` | Couldn't be sent - the upload was incomplete | Open to review, re-mark when appropriate, or Delete with confirmation. |
| `corrupt` | This couldn't be sent - contact the office | Contact office; Open/Delete remain available. |
| `unsupported` | This couldn't be sent - contact the office | Contact office; no promise that retry changes the version. |
| `not-yours` | This couldn't be sent - contact the office | Contact office; never change the capturing rep. |
| `id-in-use` | This couldn't be sent - contact the office | Contact office; never silently assign another identity. |
| `too-large` | This couldn't be sent - contact the office | Contact office; do not truncate captured work. |
| Unknown, absent, or non-actionable reason | This couldn't be sent - contact the office | Keep raw reason for support, hidden by default. |

All six codes in `UploadFaults` are technical faults. The receiver does not query business data to
reject reassignment, archive or catalogue changes (BR-NEW-006). `Received` and `AlreadyReceived`
confirm Sent. Authentication, connection and server failures retain WI-040/041's recovery paths;
they are not routed into this mapping just because an HTTP request failed. If implementation finds
an actual business-rule rejection, stop and report as required by the source brief.

Raw rejection metadata must remain separate from the captured JSON sent to the receiver.
Persist code/detail (bounded by an explicit response-read limit) with the Needs Attention state;
do not show raw JSON, server codes or arbitrary server detail in the default UI.
