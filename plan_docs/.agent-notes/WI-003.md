## Source boundary

T-1.0.2 / IAM-US-002 S1–S3: a removed Head Office User role denies the next website catalogue read and action in the open session, without restricted content, while held areas remain usable. I-05 explains a denied read or write. The work package requires characterisation first, then live role checks, I-05, and the Human-Led scenario run. The item is Human Tight-Loop, Moderate complexity, High risk, Medium confidence. WI-004 owns catalogue domain operations.

## Approved decisions

1. Use one current-role source: the identity host's ASP.NET Identity role membership. Add a narrowly scoped, bearer-protected self lookup for current business roles using the existing `fieldsales.api` token scope and `fieldsales-api` audience. The response is for the token's own `sub`; it accepts no caller-supplied user id. Website cookie validation and the API authorization boundary use this lookup on every protected request. A failed lookup denies access without using stale claims. In Increment 2, prove token validation and fresh role membership before relying on the path. No new client secret or role names.
2. If a role changes during an open website session, replace its business-role claims with the current set before authorization. Clear a last-used area that is no longer held. Subsequent routing opens the one remaining area or offers I-02 when several remain, without another sign-in. Keep the session available for I-05 and sign-out if none remain.
3. Use the I-05 layout proposed in `uxdocs/07-access-and-sign-in.md`. Show the “not saved” sentence only for a denied write. Offer only current permitted areas; if none remain, offer sign-out and the existing administrator-contact guidance. Keep the generic denial for an area never held in this session.
4. Because WI-004 owns catalogue writes and WI-003 has no production save handler, use a test-only protected Head Office POST probe with a durable test marker. Its permitted write succeeds; a stale open form after role removal cannot change that marker. Production gains no invented catalogue action.

## Approved increments (one approval/review at each boundary)

1. **Characterise:** Agent authors the approved characterisation tests in `FieldSales.Web.Tests` and `FieldSales.Api.Tests`: permitted and denied direct reads, a permitted/denied representative write, sign-out, and last-used routing. Human reviews the tests and evidence. No production authorization change in this increment.
2. **Enforce:** Human owns the shared authorization rule and its security review. Proposed touch points are the identity host, `FieldSales.Web/Security/StaffCookieEvents.cs`, `FieldSales.Api/Program.cs` and focused security services. The rule validates the caller token, resolves current roles per protected request, refreshes the website principal before role policies run, applies the same boundary to API requests, denies closed on lookup failure, and clears stale last-used preference in `StaffAreaService`. Agent performs only specifically agreed mechanical edits or agreed test work.
3. **Explain:** Agent builds the I-05 page sliver in `FieldSales.Web/Pages` from the human-approved read/write states and remaining-area list. Human owns the connection from role denial to that page and verifies it cannot expose restricted content. Agent does not implement the role check as part of the page sliver.
4. **Verify:** Agent authors and runs the agreed T-1.0.2-S denial tests; human reviews outcomes. Run full solution tests, build, admin UI and console tests. Mark WI-003 `done` only when all acceptance criteria pass, then commit and push the feature branch. Do not merge it.
