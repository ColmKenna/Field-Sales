## Approved scenarios

- First Active link becomes Main automatically.
- One person can be Main independently at several shops.
- Selecting a different Main requires confirmation and keeps outgoing links.
- Inactive/unlinked replacements are rejected.
- Existing protected removal paths cannot bypass replacement rules.
- Existing Sean replacement unlinks Mary at the selected shop only.
- New contact creation/replacement/unlinking is atomic.
- No replacement retires globally, retains links, flags affected shops.
- Retirement flags two/five shops where the person was Main.
- Naming a Main clears only that shop's gap; Mary remains Inactive.
- Reactivation never restores Main or clears unresolved flags.
- Non-Main unlink preserves existing Main choices.
- Invalid/cancelled actions write nothing.
- Concurrent/stale actions reject without partial changes.
- Missing authorization/antiforgery denies actions; restart/upgrade preserves state.

## Checkpoint design

Store nullable RetiredMainContactId on Location, distinct from Active MainContactId.
ReplacementNeeded is derived from that durable reference, not current status.
Retirement clears Active Main and records outgoing person, retaining their link.
Only explicit SetMain clears the gap; reactivation and first-link repair skip gaps.
SQL guards and restrictive references extend WI-018 together. The gap remains
queryable for WI-144, and the outgoing inactive person's identity is available
for WI-036 without adding a tablet or gap-list UI.
